# 炎上消防隊：水與火的體驗重整工作計畫

日期：2026-11-10。版本：討論稿 0.2。狀態：**已確認 A 淺水灘方向，尚未開始實作**。

本次只訂目標與驗收，不修改程式、場景或公開版本。使用者不需要指定演算法、Shader 或套件；代理負責把想要的行為轉成技術方案，並提供能比較、能否決的實機證據。

## 1. 真正目標

第一關的策略順序先保留：接馬桶水 → 清出部分通道 → 到倉庫換蘇打粉 → 熄滅油鍋。布丁、破門、救援、倒數不在本次重新設計範圍。

水不是跟在游標後面的特效，也不是一根透明藍棒：它離開噴嘴後有飛行與重量感，撞到表面才散開，落地後成為場景中可持續觀察的水。水遇到火，火勢、蒸汽與地面狀態必須連成同一個可讀的反應。

「半現實、半卡通」暫定為：行為可信、外形適度誇張、在目前俯視鏡頭下容易看懂；不追求寫實電影流體，也不接受玻璃珠／黏膠棒／一排火圖示。

## 2. 為何上一輪仍不滿意

已核對目前報告與責任邊界：

- 有實際彈道、碰撞與推力，但「有物理」不等於畫面像水。
- FireField 有 Wetness／WaterRemaining，能代表暫時濕潤；尚不是有體積、方向、會擴散合併並被障礙阻擋的積水。
- 水柱、接觸飛濺、濕痕、火焰仍像分開的效果，缺少持續的物質變化。
- 火主要仍是離散直立火舌，危險區是另一片地面色塊；與家具、地面和水的接觸感不足。
- 先前測試證明了特定程式契約，不能據此宣布水感、美術或使用者驗收通過。本次使用者明確未接受目前效果。
- 工作方式需改成先定可見結果、在小場景證明，再整合。不能再用一連串顏色／粒子數微調代替方向確認。

## 3. 建議體驗規格（待討論）

### 空中的水

- 使用者已改定方向：**不要一條完整的管狀主水柱；改為有厚度、較寬的水滴束**。這取代前稿「一道主水柱」要求。
- 水滴有實際位置、速度與代表水量，受重力與碰撞影響；整束中心較密、邊緣自然散開，不排固定幾行、不等距、也不向所有方向隨機撒。
- 「更閃」暫按「更散、噴幅更粗」理解，尚未確認是否也指反光閃爍。不將高亮閃爍當作本次目標。
- 物理採樣是水滴，不代表美術必須畫成獨立玻璃球；相近水滴在視覺上形成柔和、不規則的短水團／水片，少量邊緣飛濺保持可讀。
- 轉向時，已噴出的水沿原軌跡飛，不整條瞬間跟著轉。
- 放開按鍵後停止供水；空中的剩餘水繼續落下，不瞬間整條刪除。
- 水碰牆、地板、可動物件後，沿相應表面散開；不穿牆、不從接觸點憑空生出大量水。

### 地上的水

- 噴同一處能看見積水增加；掃射留下一段相連的水，而不是分離圓形貼圖。
- 相鄰積水會合併、鋪開，遇牆及家具底座不穿過。
- **已確認 A：薄層積水，不做房間水位上升。** 水滴落地後轉入地面水量，累積、鋪開並合併成水灘；不是撞地後刪掉水滴，再另播一個無關的貼圖。
- 第一個試作先不讓冷地面的水自動消失，以確認「真的留下來」；正式乾燥／蒸發速度在行為通過後再定。
- 具體保留時間、乾燥速度、是否整局保留，待使用者確認。超出體積／模擬上限時需有明確處理，不以固定壽命偷偷刪水冒充物理。
- 本階段不默認加入游泳、浮力、滑倒、電擊或水位解謎。

### 水遇火

- 白色／灰白蒸汽由真正的水火接觸產生；一般燃燒的灰黑煙是不同層。
- 噴到冷地板只有水花和濕地，不能也冒同樣的「滅火煙」。
- 在水實際抵達後，接觸處火變弱、出現蒸汽，逐步露出濕地／熄滅區；不是整片火瞬間消失。
- 蒸汽的大小與持續時間對應接觸反應；飄升後散開，但不遮住玩家、路線與剩餘危險區。
- 油鍋保留既有特殊遊戲規則：不能把普通地面火的水反應直接套用到油鍋，也不能讓水沿地面流動就繞過蘇打粉解法。

### 為之後有限水量預留

- 使用者確認未來會限制水量；目前先設計可核對的水量轉移，不先加入容量 UI 或改第一關供水難度。
- 同一份水只能處在一個狀態：來源剩餘、空中水滴、地面積水、已蒸發／排出。飛濺拆分與落地合併只能轉移水量，不得複製。
- 白色蒸汽依真正的水火接觸與蒸發量顯示；特效顆數不等於水量，也不能額外扣水／滅火。
- 同水量下較寬噴幅會分散覆蓋密度；不能因畫面加粗或加水滴，就憑空提高總滅火能力。實際策略平衡留到整合階段驗收。

## 5. 技術方向：先做可證明的小方案

以下是待步驟 2 驗證的方向，不是已完成或已批准的實作：

- 沿用 SprayEmitter 的實際發射／碰撞入口，不因視覺好看另開一套傷害或滅火邏輯。
- 空中水與地面水分別處理：空中用帶水量的水滴／水團物理樣本，取消必須串成單條管的呈現前提；地面試作有水量的局部薄層流動資料與連續水面。不是往現有 wet mark 上疊更多球。
- 不預設每個可見水滴都要獨立 GameObject／Rigidbody；具體模擬與合併呈現方式由小場景比較決定。不能為了大量水珠拖垮操作，也不能只剩看起來有水、實際沒有水量的粒子。
- 場景碰撞／高度與障礙決定流向，渲染只讀狀態。地面資料格可以不可見，不能畫成正方形水塊。
- 先解決目前平地房間與障礙；檯面落水、不同高度與排水納入技術試作風險，不能宣稱地面方案自動處理任意 3D 表面。
- ElementReaction 保持反應責任；統一決定水火接觸的結果，再由呈現讀取蒸汽。現有 Wetness／WaterRemaining 與新水量不能各自成為互相矛盾的權威來源。
- 水的保留不代表可反覆無限滅火：必須定義一次反應消耗／轉移的水量與熱量，避免目前即時命中與後續積水都對同一份水完整計算。
- 若小方案無法達到「真流動、積水合併、視覺連續」，停在技術驗證，提出替代路線及成本；不持續在失敗方向上修 Shader。
- 不預設購買／安裝流體套件，不更換渲染管線；有需要時先研究相容性、授權及成本，再取得同意。

## 6. 我如何監督自己的品質

- 先寫可見結果，再寫程式。每輪只解決一個主要問題，註明什麼不改。
- 固定比較條件：同一來源、水量、鏡頭、光照、背景；同時給正常視距與必要特寫。
- 每次交付包含轉向、停噴、接觸、殘留，不只挑最好看的一幀。
- 明確區分「功能測試通過」「畫面已由代理檢查」「使用者接受」三種狀態。
- 未通過畫面門檻，不以新增測試數、更多粒子或漂亮概念圖宣布完成。
- 留下失敗版本與原因；驗證副本／證據不要再放在會被 Unity 關閉時清理的 Temp 下。
- 保留可回復的現行第一關，不刪舊模型、不改團隊提供資產、不自動發布。
- 視覺量、模擬格數與噴口數要有上限；以等條件實測資源用量，不承諾尚未量測的四人效能。
- 每階段用最小相關測試；通過一階段不代表整關／多人也通過。
